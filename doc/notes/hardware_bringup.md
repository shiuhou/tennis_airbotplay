## 2. 官網核對：採用哪些資訊，修正哪些說法

來源集中於[SOURCES](../../.agents/docs/SOURCES.md#airbot-play真機控制來源2026-11-19)，以下是查閱當日官網內容，不是本台設備回報。

- **版本屬實，但不是升級指令。** 官方下載中心列2026-03-13的V5.2，主程序5.2.5、SDK5.2.3；Python入口為arm_sdk／AirbotClient，有Lease機制。需先核對實機是否相容，再決定是否需要升級；不混用舊AIRBOTArm與新版API。
- **狀態單位已確認。** angles=rad、velocities=rad/s、efforts=電流A。電流不能直接改名torque_Nm。MOS溫度官方只標4–6號馬達支援，不把缺值補零或當故障。
- **官方查詢範例不一定只讀。** [API範例][examples]的關節／馬達查詢段會先acquire_control，再enter_gravity_compensation_mode。H1不能整段執行；要核對版本後，只採查詢API與必要的生命週期處理。
- **建構client就會連線。** 官方說AirbotClient預設連localhost:50051；所以不能把建構物件當純套件檢查，也不能直接假設此地址是你的服務端。
- **軟體急停也有權限條件。** 官方API寫set_arm_emergency_stop(True)需要控制權，恢復不需要；回傳True描述的是指令成功發送，不是實際已停止的量測證明。只讀監測端不能被假設為可靠急停端。
- **release／close不當停止證明。** 文件描述釋放控制權與客戶端資源，未給出足以保證所有已接受軌跡都被取消的契約。正常完成、取消規劃、急停、失聯及Lease到期的行為需分別確認。
- **頻率分層。** 官網servo_control標預設250Hz平滑迴圈；這不是已量到的Python RPC頻率，也不自動等於policy頻率。PACE原版50Hz、M5碰撞物理960Hz、SDK通訊與控制器內迴圈是不同層。
- **硬體接口按版本看。** 現行文件區分USB-1相機與USB-2控制；實機版本未知，先核對面板標識，不憑相同Type-C形狀選孔。底座按鍵標為零點校準，不把它當急停鍵。
- 原附件兩個/en/英文連結回傳404，已換成/document/下可訪問頁面。附件中的「韌體更新服務互斥」「禁止帶電插拔」等操作要求仍需按本台相符手冊／升級流程確認；本輪不據此產生刷寫或接線指令。

倉庫附帶的《產品簡介 - AIRBOT Documentation.pdf》硬體接口章節也寫明USB-2（Type-C）連主機控制、USB-1傳末端相機資料；Python接口PDF使用can0作通訊接口範例。USB是實體連接，can0是軟體接口名稱，實際命名／驅動仍待核對，不能由範例推定本機已配置。PDF版本尚未確認，不直接執行其運動例程。

## 3. 版本未知時，現在先做什麼

**在之後要控制AIRBOT的那台電腦上盤點。** 不是隨便在Isaac容器、相機venv或遠端GPU主機執行。這一步不需要讓手臂動，也不要先安裝最新版。

若該電腦是Linux，可逐條執行以下主機資訊查詢：

```bash
cat /etc/os-release
uname -m
python3 --version
command -v arm-sdk
# Debian／Ubuntu才使用；查本機已安裝套件資料
dpkg-query -W -f='${Package} ${Version}\n' airbot-arm
# 在實際預計使用的Python環境查套件，不import SDK、不連設備
python3 -m pip show arm-sdk
```

找不到命令或套件就如實記「此環境未找到」，**不能推論整台電腦所有venv都沒安裝**。若不是Linux，先提供OS與目前安裝方式，不硬套上述命令。此處不執行sudo、啟動服務、CAN設定、examples run或client連線。

同時從購買文件、銘牌或既有設定補下面資料；無法辨識保持未知：

| 欄位 | 填寫內容 |
| --- | --- |
| 硬體 | AIRBOT Play具體版本／型號；識別資訊留本地 |
| 控制電腦 | OS、架構、Python環境 |
| 已裝軟體 | airbot-arm服務套件版本、arm-sdk版本、安裝來源 |
| 連接方式 | 電腦到哪個面板接口；是否有USB-CAN／其他轉接；服務跑在哪台主機 |
| 現有狀態 | 是否有其他控制程式、服務或使用者；不為盤點而切換模式 |
| 現場停止 | 實際能用的停止裝置／程序，由本台手冊核對 |
| 安裝照片／圖 | 底座、桌面、球拍及周圍障礙；不為拍照去拖動手臂 |
| 韌體 | 暫未知；後續核對安全查詢路徑再讀 |

下一個交付是這份**真實盤點結果**，不是一份已填5.2.5／5.2.3的預設配置。本輪尚未建立空資料集或自製真機控制器。

## 5. H1為什麼只讀也要先核對範例

先確認本台支援的SDK，再優先找官方查詢入口。若官方現成例程包含控制權或模式變更，才補最小只讀記錄層，不另造通訊協定或SDK。

建議的資料流（尚未實作）：

```text
已確認的官方client／服務
  → 狀態查詢（無acquire、模式切換、回零、清錯或運動）
  → 保存SDK原值及查詢開始／結束的host monotonic時間
  → 檢查維度／單位／缺值／故障
  → 週期與狀態有效性報告
```

- 有效期、快取／新樣本、錯誤回傳與連線timeout須先看該版本契約；不能因呼叫成功就假設是新量測。
- 主機輪詢間隔只能說明輪詢節奏；缺少裝置sequence／timestamp時，不能精確宣稱裝置丟樣率或單向延遲。
- get_arm_joint_state與get_arm_motor_state是不同呼叫，不假設兩份回報同時採樣。
- 靜止資料能核對數量、零位和時序，**不能單憑靜止證明每軸正方向**；正方向需H2受控小幅運動。
- 只讀階段不清錯、不自動恢復急停、不進重力補償。故障原值先保留，恢復操作另處理。

## 6. H2停止與模式選擇

planning_control是首次低速運動的候選，不是未核對版本就選定的模式；也不能假設其內建規劃已知我們的桌子和自製球拍。需另確認碰撞幾何與路徑淨空。

對每種準備使用的模式先填「輸入單位、指令是否排隊／覆蓋、blocking語義、速度／加速度限制、接受回覆、取消／正常停止、故障、失聯／Lease到期、恢復方式」。欄位未知時不推斷。

停止實驗要區分：

1. 正常走完短路徑後是否靜止。
2. 以官方支援途徑取消／中止後，停止時間與位移。
3. 現場急停在該安裝、負載、姿態下的行為，及復原是否會續跑舊命令。

不能透過任意斷電或中途kill來代替已評估的停止試驗；不能把API返回成功直接標為停止PASS。任何非預期運動、接觸、狀態失效、控制權衝突或未解故障都中止當次測試並留證據。

## 7. H3沿用已有模型，避免多一套FK

使用[kinematics.py](../../src/airbot_tt/kinematics.py)與[tool.py](../../src/airbot_tt/tool.py)、[已確認工具配置](../../configs/racket.json)。既有Kinematics的tcp_transform相對flange；tool.py會由link6到TCP的幾何轉換換算，不可混用。

```text
T_world_TCP = T_world_base · T_base_link6(q) · T_link6_TCP
```

先列J1–J6到URDF名稱、順序、正負號、單位與零點offset，再把同一組實測q送入FK。SDK的end pose可能是法蘭或SDK設定工具，不預設就是我們的拍面TCP。

在數個經核准的安全姿態，用獨立量具／幾何參考檢查球拍中心、法線及底座安裝。**把同一組q送進兩份相同FK只能驗證軟體一致性，不能證明真機TCP位置正確。** 量具精度不足就交粗驗證，不報毫米級結論。相機／手眼留到後續。

## 8. H4量什麼，怎麼服務PACE

- **位置／速度追蹤**：每軸RMS、P95、最大值；對齊目標與實際回報的時間軸，保持原始資料。
- **延遲與抖動**：保存指令發出、回覆和查詢接收時間；有裝置時鐘才進一步做時鐘對齊。互相關只能估計整體相位延遲，不直接等同網路單向延遲。
- **控制頻率**：分開測主機下令、回報、控制器內迴圈；報P50／P95間隔。觀察缺值／超時，無序號時不虛構丟包數。
- **停止**：預定靜止速度門檻和維持時間，計中止至停穩耗時、各軸位移及TCP位移。
- **247g負載**：電流、溫度、故障與姿態相關性；沒有馬達常數／傳動標定，不由efforts直接計Nm。
- **仿真對照**：同起始q、同負載近似、同路徑、同時間參考。保留實測誤差，不能用理想命令曲線替代實際動作。

目標是據實測選policy控制接口、週期、action scale及延遲／飽和模型，不因官方將MIT標為「RL推理」就優先上MIT。H4結果可供後續仿真建模，但不自動改動已凍結的M5或PACE對照配置。
